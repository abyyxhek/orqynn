# Orqyn (director-brain) — Architecture & Engineering Audit

**Date:** 2026-10-04
**Scope:** Full architecture review and audit of the workspace — committed history
and the uncommitted working tree — with all gates re-run from a clean build, and
both live substrate suites executed.
**Auditor:** Claude Code, at the author's request, for review by a senior engineer.

---

## Executive summary

Orqyn is a vendor-independent **orchestration brain** for multi-agent software
work. It sits *above* the coding agents (Claude Code, Codex, DeepSeek, OpenCode,
Goose, Cursor) and *beside* two existing substrates — `handoff-mcp` (tasks,
sessions, agents) and `ai-memory` (long-term memory) — which it talks to
**exclusively over MCP** and never by importing their types.

The project is delivered as a four-crate Rust workspace with a strictly one-way
dependency direction, a substrate boundary enforced by a **test** rather than a
convention, and two load-bearing invariants expressed in the type system rather
than in prose. All six steps of the control loop
(`OBSERVE → PLAN → ASSIGN → MONITOR → VERIFY → REPLAN`) plus a `SCHEDULE` step
are landed and tested.

**The audit found no design defects and no correctness bugs.** Every gate passes
clean on a from-scratch rebuild:

| Gate | Result |
|---|---|
| `cargo fmt --all -- --check` | ✅ clean |
| `cargo clippy --workspace --all-targets -- -D warnings` | ✅ clean |
| `cargo build` | ✅ clean |
| `cargo test --workspace` | ✅ **494 passed**, 0 failed, 13 ignored |
| Live substrate suites (run separately, `--ignored`) | ✅ **13 passed** (8 ai-memory, 5 handoff) |

**Total: 507 tests green**, including 13 that exercise the real substrate
servers over a real stdio JSON-RPC connection.

The audit's findings are process and hygiene, not correctness — the largest is
that Phase 7 (the scheduler) and the Phase 10 verification-record layer are
uncommitted and, in Phase 7's case, **unpushed**, so no off-machine copy of the
scheduler exists. Details in §6.

## 2. Architecture

### 2.1 The shape of the system

Orqyn owns the parts neither substrate has — planning, assignment, checkpointing,
independent verification, recovery, and replanning — and reuses the parts they
already do well rather than reimplementing them. handoff-mcp becomes the
task/session/agent substrate; ai-memory becomes the memory/retrieval substrate
(FTS5, entity, and graph retrieval with decay are already solved well there).

```
                    ┌─────────────────────────────────────────────┐
                    │            ORQYN                             │
                    │  owns: plan, task, assign, verify,          │
                    │   checkpoint, recover, replan, context       │
                    │                                             │
                    │   ┌───────────────────────────────────────┐  │
                    │   │  Canonical domain model (Orqyn's       │  │
                    │   │  OWN entities + provider TRAITS)       │  │
                    │   └───────────────┬───────────────────────┘  │
                    │                   │                          │
                    │   ┌───────────────▼───────────────────────┐  │
                    │   │  HandoffAdapter      MemoryAdapter     │  │
                    │   │  (TaskProvider,      (MemoryProvider,  │  │
                    │   │   AgentProvider,      ProjectState-     │  │
                    │   │   SessionProvider)    Provider)         │  │
                    │   └───────┬────────────────────┬───────────┘  │
```

### 2.2 Crate structure

Four crates, strictly one-way dependencies. Verified: no crate outside
`director-adapters` declares or references `handoff_mcp` / `ai_memory` in code
or in `Cargo.toml`.

| Crate | Src lines | Role | Depends on |
|---|---|---|---|
| `director-domain` | 7,686 | The vocabulary: every entity, 16 identity newtypes, status enums, and the 7 provider traits. Knows no substrate. | nothing |
| `director-adapters` | 7,047 | The proof: `InMemoryProvider` (all traits, in-process), `LocalExecutor` (real command execution), the git observation layer, and live MCP clients for both substrates. **The only crate allowed to name a substrate.** | domain + both substrates |
| `director-store` | 5,009 | SQLite persistence for Orqyn's own entities. Owns its schema; three migrations (380 lines of SQL). | domain only |
| `director-app` | 5,026 | The control loop. Composes the layers into steps; all six steps plus the scheduler wired in. | domain + store |

documentation that records not just what was built but what was *rejected*.

### 2.3 The two load-bearing invariants

Both are enforced in the types, not in the docs, and both are what the model
exists to express.

**1. Task identity is independent of agent identity.**
`TaskId` and `AgentId` are distinct, sealed newtypes — neither can be constructed
from the other, so a task id can never be passed where an agent id is expected.
`Task` has **no agent field**; assignment is a separate first-class entity
(`AgentAssignment`) with its own history. Reassigning a task creates a new
assignment record and changes nothing about the task itself. Three agents can
work a task in turn and the task's identity is byte-identical before, during, and
after, while the full tenure history remains recoverable. Tests confirm this.

**2. Nothing self-reports completion.**
`TaskStatus::Done` is **not reachable** from an agent's report. There is no
provider method an agent can call that completes a task. Only Orqyn's own VERIFY
step can do that: it runs the machine-checkable commands a plan named for the
task's expected outputs and reads their exit codes itself — the agent whose work
is being judged never gets to report the outcome, and the provider that runs a
command never gets to interpret it. A **live test proves it against the real
handoff server**: `an_agent_done_does_not_complete_but_a_director_done_does`
(re-verified green during this audit).

This is the guardrail behind the acceptance criterion *"Agent claims 'Done.'
Tests fail → must not become COMPLETED."* Both substrates were audited in Phase 0
and neither satisfies it: handoff-mcp's `handoff_check_criterion` is a
self-reported checkbox tick, and ai-memory has no task model at all.

### 2.4 The boundary is a test, not a convention

`crates/director-adapters/tests/boundary.rs` walks the workspace and **fails the
build** if any `.rs` file outside `director-adapters` contains the identifiers
`handoff_mcp` / `ai_memory`, or any `Cargo.toml` outside it declares a
dependency whose name contains `handoff` / `ai-memory`. It deliberately matches
only the identifiers a `use` statement would need — doc comments that *name* the
substrates to explain why Orqyn differs from them are correctly allowed, because
that rationale is the opposite of coupling. It also asserts the expected crates
exist, so it cannot silently pass on an empty tree. **Re-verified: 3 tests
passing.**

This is the single best decision in the codebase. A developer can intend the
boundary and still break it with one misplaced `use`; the test makes the
intention executable. It has held across seven subsequent phases of work, and it
inspired a sibling test — `wiring.rs`, added after the audit of 2026-09-30 found
a 610-line step module that had never been compiled:

> `crates/director-adapters/tests/wiring.rs` fails the build if any `.rs` file
> under a crate's `src/` is not reachable from the module tree. An undeclared
> file is invisible to cargo, so a file written but never wired in compiles
> nowhere and its tests never run. It exists specifically because `plan.rs` once
> sat uncompiled for days. **Re-verified: 1 test passing.**

### 2.5 The provider trait boundary

Seven traits, all `async`, all returning Orqyn's own types, each with an
associated `Error`:

| Trait | Purpose |
|---|---|
| `TaskProvider` | CRUD, status, `ready_tasks`, dependency edges |
| `AgentProvider` | Registry, heartbeat, availability |
| `SessionProvider` | Lifecycle, per-task history, fork |
| `HandoffProvider` | Orqyn's claim-once transfer |
| `MemoryProvider` | Durable knowledge, query, recency |
| `ProjectStateProvider` | Observed git/filesystem state |
| `ExecutionProvider` | Run real commands; Orqyn reads the exit code itself |

Four rules are baked in: methods are `async` (every real substrate is an I/O
boundary); inputs and outputs are Orqyn's types, never a substrate's struct;
each trait has an associated `Error`, so a substrate's failure vocabulary cannot
become Orqyn's; and **nothing here completes a task**.

Deliberately absent from the traits: checkpoint, plan, decision, blocker,
verification, and assignment storage. Those are Orqyn-owned entities in Orqyn's
own store. Exposing them as provider traits would invite a substrate to become
authoritative over Orqyn's own state.

The adapters that implement these traits each follow the same four-layer shape —
`wire` (serde mirrors of the substrate's JSON, deliberately not the domain
types), `transport` (the MCP client), `mapping` (the bidirectional translation),
`adapter` (the trait implementation) — so the two substrates read as one pattern,
and the mapping logic is unit-testable without a child process.

The `mapping` layer is where the earned keep is. The two models are not
isomorphic: handoff-mcp has 6 task statuses and Orqyn has 8, so Orqyn-only
states ride in the substrate's `extra` map rather than being forced into the
nearest fit. Critically, handoff-mcp's `done` is an agent self-report, so it
becomes `VerificationPending`, not `Done`, unless Orqyn itself produced it. The
`AiMemoryAdapter` shows the same discipline on a different surface: it keeps the
two meanings of a `rank` field separate — a relevance score from `memory_query`
and a change time in microseconds from `memory_recent` — rather than collapsing
them.

### 2.6 Persistence design

SQLite via a migration runner, three migrations:
`0001_initial.sql` (279 lines), `0002_plans_decisions.sql` (62),
`0003_verifications.sql` (39, uncommitted). Three design choices worth calling
out:

- **Schema-level invariants over conventions.** "At most one active plan per
  project" and "at most one active assignment per task" are partial unique
  indexes in the schema, so they hold even for a caller that bypasses the
  repository. Tests prove a rogue write inserting a second active plan is
  *rejected* rather than silently creating a second authoritative plan.
- **Superseding, never deleting.** Activating a plan marks the previous one
  superseded and links both ways; the superseded plan survives as audit trail.
  Reversing a decision marks it, not deletes it, and cannot be reversed twice.
  Stale writes yield `StateVersionConflict` rather than overwriting newer state.
- **Atomic operations own the state moves.** `assign_and_start` folds the
  handoff, the task's move to `in_progress`, and the status-transition row into
  one transaction. `apply_verification` (uncommitted) folds the verification
  row, the task's status move, and the transition history. `cancel_task` folds
  the move to `cancelled` and the `Decision` recording why. A refused request
  writes nothing, everywhere.

One hard-won subtlety is documented in the schema and worth a reviewer's
attention: **enum columns are stored as JSON-quoted strings** (`"active"`, eight
characters including the double quotes), so any *static* SQL in a partial index
or CHECK constraint must compare against the quoted form — `WHERE status =
'active'` matches nothing and the rule is **silently unenforced**. This bit both
partial indexes in `0001_initial.sql` during Phase 5; it is now correct, the new
`0003` migration documents it inline, and it is covered by an integration test
that inserts through the repository the way a caller does.

### 2.7 The control loop

Built one step at a time, in the order the steps run, each landed and tested
before the next was written:

```
OBSERVE (git/fs + substrate events + agent heartbeats) ✅
   → PLAN / REPLAN (grounded in observed state) ✅
      → SCHEDULE (which ready task goes to which agent) ✅
         → ASSIGN (claim lease via the handoff) ✅
            → MONITOR (heartbeat TTL, lease expiry, progress reports) ✅
               → VERIFY (runs the plan's named checks itself) ✅
                  → UPDATE STATE → loop back, or RECOVER on failure
```

Each step is a small module in `director-app` that composes the layers
underneath it, with a flat, source-free error enum whose variants name the ids
involved, because "cannot assign" is not actionable. Steps that *refuse* work
refuse before writing anything; steps that *report* (a refused pairing, a
stranded dependent, a quiet agent) return the report rather than raising, so a
world that changed mid-round does not look like a transient retryable fault.

Two design points a reviewer should appreciate, because they are easy to get
backwards:

- **`Unverifiable` is not a failure.** A check that cannot run is a property of
  the environment, not a verdict on someone's work. A broken harness marking
  work `failed` would make every environment hiccup a false verdict. So an
  unrunnable check leaves the task awaiting verification and writes nothing —
  which is also what makes it safe to resurvey next tick.
- **A quiet MONITOR round is a full report, not an empty one.** Every task in
  flight is reported `Live`; "nothing in flight" and "everything fine" differ.

## 5. The uncommitted work — Phase 10's record layer

The working tree contains the persistence foundation of the verification engine:
~1,200 lines across three new files plus a migration, and **23 new tests** (8
domain unit, 9 store unit, 6 store integration — the difference between the
committed 471 and the working tree's 494).

What is there:

- **`director-domain/src/verification.rs`** (539 lines) — the entity model:
  `Probe` (four kinds: `Command`, `TestSuite`, `Diff`, `File`), `Evidence`,
  `EvidenceStatus` (`Passed` / `Failed` decide; `Unverifiable` means the evidence
  could not be gathered and is *not* a failure of the work; `Observed` is
  advisory and decides nothing), `VerificationStatus`, and `Verification` itself.
- **`director-store/migrations/0003_verifications.sql`** (39 lines) — the
  `verifications` table plus task and project history indexes.
- **`director-store/src/verifications.rs`** (625 lines) — `SqliteVerificationRepository`
  and `Store::apply_verification`.
- **`VerificationRepository`** trait in `director-domain/src/store.rs`, and
  `VerificationId` in `ids.rs`.

Three design decisions in this work are worth a reviewer's attention, because
each one is a place a less careful design would have created a subtle bug:

1. **A verification is append-only history, not a mutable record.** Re-judging a
   task writes a *new* row with a new id; there is no update path and no delete
   path. So "Orqyn judged this task three times — it failed twice on a broken
   suite and passed on the third attempt" is an ordinary query rather than a
   forensic reconstruction from logs. A duplicate id is a constraint violation,
   because two verifications with one id is a judgment history that has lost a
   row.
2. **`apply_verification` is one transaction doing three writes**, and the task's
   destination is *derived from the verdict* rather than taken from the caller.
   The window between the verification row and the status move would be a task
   that reads `done` with no recorded judgment — and `done` is the status the
   whole model exists to make unreachable without independent evidence, so a
   `done` with no verification is not a degraded record, it is a broken
   invariant. `VerificationStatus::task_status()` is the single place the
   mapping lives, so the store and the step cannot disagree about what `Passed`
   means. An `Unverifiable` verdict still writes the verification row — "Orqyn
   looked, and could not yet tell" is history worth keeping — and moves nothing.
3. **The evidence column is read and written as one unit with its verification.**
   Nothing ever selects "all verifications whose evidence contains a failure", so
   a join table would buy nothing and cost a consistency boundary. And a
   malformed column is a deserialization *error*, never a silent default — an
   evidence column that silently deserialized to `[]` would present a judgment
   Orqyn reached as one it reached on no evidence at all.

**What is not there:** the engine. Nothing in `director-app` references the
verification entity yet — `apply_verification` has no caller outside tests. The
module that *runs* the probes, gathers evidence, and applies precedence rules is
not written. The existing Phase 6 VERIFY step continues to hold the invariant on
its own, judging tasks by the checks a plan named.

This is the right order to build it in — the record layer is the seam the engine
writes through, and landing it first means the engine's output is durable from
its first test run. But it is uncommitted, and it should be committed before more
of the engine is layered on top of it.

## 6. Findings

### F1 — Phase 7 is unpushed; no off-machine copy of the scheduler *(medium)*

`main` sits 0 behind / 3 ahead of `origin/main`. The three unpushed commits
(`2e1f4fa`, `f3321b5`, `1a166df`) are the entire Phase 7 deliverable — the
scheduler, its docs, and the README update. There is no second copy of this work
off the machine. Everything else through the 2026-10-02 stabilization *is* on the
remote; only Phase 7 is exposed.

**Recommendation:** push before or alongside the Phase 10 commit. This is the
only finding that risks real loss of work.

### F2 — The Phase 10 record layer is uncommitted *(medium)*

See §5. ~1,200 lines of well-tested code sitting in the working tree, including a
new migration. The project's own history shows this exact pattern is expensive:
code written without a compile loop accumulates a whole phase's worth of errors,
and uncommitted work has repeatedly been found in worse state than claimed. Here
the work is genuinely green — it compiled, passed clippy, and all 23 new tests
pass on a clean rebuild — but it is one disk event from being lost alongside F1.

**Recommendation:** commit the record layer as its own commit now. It is
self-contained: a domain entity, a store trait + implementation, a migration, and
tests. Nothing in `director-app` depends on it yet, which is precisely what makes
it a clean commit boundary.

### F3 — The README's test count is stale *(low)*

The README's status line says "a passing test suite (471 tests)". That number is
correct for the committed state and stale for the working tree, which is 494.
This project has misstated this number three separate times in notes and docs
(311 vs 299 in the previous audit, 325 vs 335 after ASSIGN, 311/299 again), and
each time the fix was to sum the per-suite table from a clean run rather than
trust a remembered figure. The per-suite table in §4 is that sum.

**Recommendation:** update the count from the table in §4 when the Phase 10
commit lands, and keep deriving it from a clean run.

### F4 — A stale duplicate checkout exists beside the project *(low)*

`../orqyn/` is a second working copy of the same repository (same GitHub remote)
parked at the Phase 2-era tip. It predates the `AiMemoryAdapter`, the entire
`director-app` crate, and the wiring test; its `crates/` differs from
`director-brain`'s in most files. It is harmless but it is a genuine confusion
risk — a reader who opens the wrong directory sees a project that is four phases
behind and missing its central crate.

**Recommendation:** delete it, or move it out of the working area.

### Positive findings

The things that were checked and held up:

- **No correctness bugs.** No test failures, no clippy warnings, no fmt drift, on
  a clean rebuild of the committed and uncommitted code together.
- **The boundary test is genuine enforcement**, and it passes against the real
  tree, not a stub. The wiring test is the same class of guard, for modules.
- **13 live integration tests pass against both real servers** — including the
  one that proves the central invariant on the real wire. Most projects in this
  category have only mock-based tests. The one that matters most:
  `an_agent_done_does_not_complete_but_a_director_done_does`.
- **The atomic operations are real, and tested by rollback.** The store's
  integration suite proves atomicity by assigning to a nonexistent agent and
  confirming the foreign-key failure rolled the whole transaction back, and now
  by confirming `apply_verification` rolls back when the task does not exist.
- **Documentation is current, not aspirational.** The README was rewritten when
  Phase 5 made "no persistence" false. Phase docs record rejected approaches,
  which is more useful to a reviewer than a clean success narrative. The one
  exception is the stale test count (F3).
- **A `.gitattributes`** (`* text=auto eol=lf`) stops `core.autocrlf=true` from
  rewriting every file's line endings on each commit — a real problem here that
  manufactured noisy diffs and conflicts.
- **History was reconciled deliberately**, not by force-push: the local line and
  the rebranded remote had no merge base, a file-by-file comparison showed
  `crates/` was byte-identical at the Phase 2 tips, so the local commits were
  cherry-picked onto the remote line with only `README.md` conflicting. The
  rename (Director Brain → Orqyn) was completed in prose while the `director-*`
  crate names stayed as-is, which is correct — the crate names are a build
  artifact, not a brand surface.

   existing work from loss. (F1)
2. **Commit the Phase 10 record layer** as its own commit — domain entity, store

   deriving it from a clean run. (F3)

5. **Continue Phase 10** with the engine itself: the module that runs the probes
   through `ExecutionProvider` and the git layer, applies the precedence rules,
   and writes through `apply_verification`. The record layer is the seam it

   ephemeral. Wire the module into `director-app/src/lib.rs` **first**, before

   driver process that would run the loop unattended (today the tests are the
   caller, which is deliberate), and decomposition — PLAN deciding *what* the
   tasks are, rather than validating a caller's decomposition.

## Appendix — How to reproduce the gates
