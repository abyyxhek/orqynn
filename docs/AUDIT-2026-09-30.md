## Executive summary

> **Resolution note (same day).** Both findings below were acted on. `plan.rs`
> is now declared as a module, compiles, and its 10 tests run; the store gained

> written, as the record of what the audit found.

Orqyn is a Rust workspace that implements a control loop
(`OBSERVE → PLAN → ASSIGN → MONITOR → VERIFY → REPLAN`) over two existing
subsystems — `handoff-mcp` and `ai-memory` — which it talks to **only over
MCP** and never by importing their types.

The architecture is the strongest thing here. Four crates with a strict
dependency direction, a substrate boundary enforced by a *test* rather than a
convention, and two invariants expressed in the type system rather than in
prose. ~21,000 lines of Rust, 299 tests plus 13 live integration tests against
the real substrate servers, and a documentation trail (1,952 lines across seven
phase documents) that records not just what was built but what was rejected.

The audit found **no design defects and no correctness bugs in committed
code**. It found a real process problem and one significant gap between the
claimed state and the actual state, both in the **uncommitted** Phase 6 work:

1. **`director-app/src/plan.rs` is dead code.** It is 610 lines implementing
   the PLAN step, but it is not declared as a module, so it has never been
   compiled and its 10 tests have never run. The README says PLAN is "built
   next"; the file exists but is not wired into the build.
2. **The uncommitted work did not compile when the audit started.** Three type
   errors and a malformed doc comment. Every gate was red. This is code that
   was written without a compile loop — the same failure mode that has now
   recurred four times on this project.

After the audit's fixes (detailed in §6), **all four gates pass clean on a
from-scratch rebuild: fmt, clippy `-D warnings`, build, 299 tests + 13 live.**

Nothing has been pushed to the remote. `main` sits **0 behind / 7 ahead** of
`origin/main`.

## 1. What was audited and how

Claims in this report were verified by running things, not by reading them.
Concretely:

- The external target directory was deleted and the whole workspace rebuilt
  from scratch. (This matters: this machine has a wall-clock desync that leaves
  future-dated artifacts, which makes cargo *skip* recompilation and run stale
  test binaries. Only a clean rebuild is trustworthy here.)
- All four gates re-run: `cargo fmt --check`, `cargo clippy --all-targets
  --all-features -- -D warnings`, `cargo build`, `cargo test --all`.
- Both **live** substrate suites executed against the prebuilt server binaries
  (8 ai-memory tests, 5 handoff tests). These are `#[ignore]` by default and
  are the only evidence in the repo about the real wire format.
- Git history, the working tree, and every phase document reviewed.
- The substrate boundary verified independently of the test that enforces it.

Toolchain note: the workspace pins `stable-x86_64-pc-windows-gnu` and this
machine has no system C toolchain, so builds require a WinLibs GCC on `PATH`.
Because the project lives under `OneDrive\Desktop`, the target directory must
be redirected off OneDrive or sync engine write locks intermittently fail
builds with `os error 32`. Both are machine workarounds, correctly **not**
committed to the repo.

## 2. Architecture assessment

### Crate structure

| Crate | Lines | Role | Depends on |
|---|---|---|---|
| `director-domain` | 7,002 | The vocabulary: entities, id newtypes, status enums, 8 provider traits. Zero substrate knowledge. | nothing |
| `director-adapters` | 7,688 | The proof: live MCP clients for both substrates. The **only** crate allowed to name them. | domain + both substrates |
| `director-store` | 5,146 | SQLite persistence for Orqyn's own entities. | domain only |
| `director-app` | 1,237 | The control loop. Currently only OBSERVE is wired in. | domain + store |

Note on the last row: `director-app`'s 1,237 lines count `plan.rs` (610), which
is **not declared as a module and therefore not compiled** (see §5, F1). The
compiled crate is ~627 lines. Figures are file counts, not compiled-code counts.

Dependency direction is strictly one-way. Verified: no crate outside
`director-adapters` declares or references `handoff_mcp` / `ai_memory` in code
or in `Cargo.toml`.

### The two load-bearing invariants

Both are in the types, not the docs:

**1. Task identity is independent of agent identity.** `TaskId` and `AgentId`
are distinct newtypes — neither can be constructed from the other, so a task id
can never be passed where an agent id is expected. `Task` has **no agent
field**; assignment is a separate first-class entity (`AgentAssignment`) with
its own history. Reassigning a task creates a new assignment record and changes
nothing about the task. Tests confirm task identity survives three assigned
agents and that assignment history is retained after release.

**2. Nothing self-reports completion.** `TaskStatus::Done` is unreachable from
an agent's report (`reachable_by_agent_report` guards this). Only a future
verification engine completes a task. A live test proves it against the real
handoff server: an agent reporting done does not complete the task, but a
Director-initiated done does.

### The boundary is a test, not a convention

`crates/director-adapters/tests/boundary.rs` (3 tests) fails the build if any
`.rs` outside `director-adapters` contains the identifiers `handoff_mcp` /
`ai_memory`, or any `Cargo.toml` outside it declares a dependency containing
`handoff` / `ai-memory`. It deliberately matches only the identifiers a `use`
statement would need — doc comments that *name* the substrates to explain why
Orqyn differs from them are correctly allowed, because that rationale is the
opposite of coupling. It also asserts the expected crates exist, so it cannot
silently pass on an empty tree.

This is the single best decision in the codebase. A developer can intend the
boundary and still break it with one misplaced `use`; the test makes the
intention executable. It has held across five subsequent phases of work.

### Persistence design

SQLite via a migration runner (`0001_initial.sql` 279 lines,
`0002_plans_decisions.sql` 62 lines). Two design choices worth calling out:

- **Schema-level invariants over conventions.** "At most one active plan per
  project" and "at most one active assignment per task" are partial unique
  indexes in the schema, so they hold even for a caller that bypasses the
  repository. A test proves a rogue `update_plan` inserting a second active
  plan is *rejected* rather than silently creating a second authoritative plan.
- **Superseding, never deleting.** Activating a plan marks the previous one
  superseded and links both ways; the superseded plan survives. Reversing a
  decision marks it, not deletes it, and cannot be reversed twice. Stale writes
  yield `StateVersionConflict` rather than overwriting newer state.

One hard-won subtlety is documented in the schema: enum columns are stored as
**JSON-quoted** strings (`"active"`, including the quotes), so any static SQL
in a partial index or CHECK constraint must compare against the quoted form.
Unquoted predicates match nothing and the rule is silently unenforced. This
bit both partial indexes in `0001_initial.sql` during Phase 5; it is now
correct and covered by an integration test.

## 3. Phase-by-phase results

Each phase has a committed document recording what was built and, usefully,
what was rejected.

### Phase 0 — Repository forensics ✅ *committed*
Read-only audit of both substrates. 724 lines — the largest doc in the repo.
Its output is the integration boundary that every later phase depends on:
**MCP only, never import substrate structs.** Also enumerated which entities
Orqyn must own itself because no substrate has them: checkpoint, plan,
decision, blocker, verification, assignment. Those live in Orqyn's own store
from Phase 5 onward and must never become provider traits.

### Phase 1 — Domain model + provider boundary ✅ *committed*
Canonical entities, id newtypes, status enums, and the provider trait boundary.
Zero substrate coupling by construction. This is the layer that makes
everything else substitutable — the adapters are exchangeable because nothing
upstream knows they exist.

### Phase 2 — Git observation + HandoffAdapter ✅ *committed*
Two halves, each independently useful:
- **Git layer:** a read-only `git2` observer, a JSON store, and a composing
  service producing `ProjectStateSnapshot`. `StateComparison` distinguishes a
  head advance from a rebase — the difference between "progress" and
  "history was rewritten".
- **HandoffAdapter:** a live `handoff-mcp` client implementing
  `TaskProvider`/`AgentProvider`/`SessionProvider`. Writes go through a real
  stdio JSON-RPC connection.

Notably it handles a non-isomorphic mapping honestly: handoff has 6 task
statuses, Orqyn has 8, so Orqyn-only states ride in `extra` rather than being
forced into the nearest fit.

### Phase 3 — AiMemoryAdapter ✅ *committed*
A live `MemoryProvider` over the ai-memory MCP server. The detail that shows
the work was verified rather than assumed: a memory search returns **full page
bodies, not `<mark>`-tagged FTS5 fragments**, and reports a change time only
on the one read path where the substrate actually sends one — i.e. the adapter
does not invent metadata the source cannot supply.

### (No Phase 4)
Deliberate. The README roadmap jumps 3 → 5 and states so explicitly. Not a
gap in the numbering.

### Phase 5 — director-store ✅ *committed*
SQLite persistence for Orqyn's own entities: checkpoints, plans, verifications,
decisions, recent context, recovery packages, assignments. Later extended with
plans + decisions (migration `0002`). Nine integration tests cover the
behaviors that matter; in particular the partial-unique-index test that proves
the JSON-quoted predicate form is correct rather than merely plausible.

Worth flagging for a reviewer: this phase **landed with zero tests and broke
four existing ones** that hardcoded "reaches version 1". Fixed by deriving the
expected version from `latest_version()` / `migrations()` so they cannot go
stale when migration 0003 lands. The fix was better than the original.

### Phase 6 — director-app ⧗ *underway, partially committed*
The control loop, built one step at a time in the order the steps run. Only
**OBSERVE** is committed and wired in — deliberately first, because it is the
only step whose inputs come entirely from outside Orqyn. It composes
`GitService` (raw evidence) with `Store` (normalized belief) and is the first
code anywhere to open a `Store`.

Two design details in OBSERVE that a reviewer should appreciate:
- The store's `state_version` is a **write counter, not a change signal**, so
  `changed` comes from the git layer's `SyncResult` instead. A version
  comparison would report every observation as a change.
- `first_observation` is reported by the registration itself, not inferred from
  `SyncStatus::Baseline`, because a repo with existing history syncs as
  `Synced` on its very first observation.

**PLAN is in progress and uncommitted.** See §5.

## 5. Findings

### F1 — `plan.rs` is not wired into the build *(high)*

`director-app/src/plan.rs` (610 lines) implements the PLAN step: `PlanRequest`,
`TaskSpec`, `Planned`, `async fn plan()`, `async fn plan_at()`, and
`grounded_rationale()`, with 10 tests. **`director-app/src/lib.rs` declares
only `pub mod observe;` — there is no `pub mod plan;`.** Nothing in the
workspace references the module.

Consequences:
- The file has **never been compiled**. Its 610 lines are unverified.
- Its **10 tests have never run**. The 299 count above does not include them.
- The crate's public API does not expose `plan()` at all.

This is the largest gap between the README's claimed state ("PLAN built next")
and reality: the work is substantially written but not connected. Wiring it in
is a one-line change that will surface whatever compile errors the file has,
and it should be done before any further PLAN work is layered on top.

### F2 — The uncommitted work did not compile *(high, now fixed)*

When the audit began, all four gates were red. Three separate defects, all in
the uncommitted `director-domain/src/graph.rs`, all mechanical:

1. **`lib.rs:41`** — the new `graph` doc-comment line lost its `//! ` prefix.
   This broke `director-domain` at **parse time**, before any type-checking.
2. **`graph.rs:184`** — `&n.id == *t` compared `TaskId` against `&TaskId`
   (double reference, because `min_by_key` passes `&&TaskId`). Fixed to `**t`.
3. **`graph.rs:202`** — `step == &start` had the same ref-level mismatch, and
   `path.contains(step)` needed `&step`.
4. **`graph.rs:312`** — a `matches!` pattern bound fields as `task` / `dependency`,
   shadowing the test helper `fn task(...)`, so `task == task("B")` tried to
   call a value. Renaming the bindings to `t` / `d` exposed a follow-on: the
   pattern then partially moved out of `err`, breaking the `"got {err:?}"`
   failure message. Fixed with `ref t` / `ref d` bindings.

Fixes 1–4 are applied. The gate numbers in §4 reflect them.

### F3 — Recurring process failure: code written without a compile loop *(medium)*

This is the fourth occurrence of the same failure mode on this project:
- Phase 2: the `done_criteria` / `task_links` mirror shapes were wrong.
- Phase 3: a `kind` → `type` transport field mismatch.
- Phase 5: the store crate had ~40 errors of 8 kinds when first compiled.
- Phase 6: four errors, and a whole 610-line file never compiled at all.

The pattern is consistent and it is expensive. Each time, source reading and
writing confirmed *intent*; only running the compiler revealed *the code*. The
phases that compiled early (2's git layer, 3's adapter after the fix, 6's
OBSERVE) are the ones with clean gate runs on first audit.

**Recommendation:** make "the new file is declared as a module and the crate
compiles" the first checkpoint of any new file, before any logic is written —
not the last step before commit. A 30-second `cargo build` here would have
caught F1 and F2 immediately.

### F4 — "Gates are green" claims about uncommitted work are unreliable *(medium)*

A prior note in this project's own records asserted Phase 5 was green; a
re-run found fmt drift at 11 sites, 2 clippy `-D warnings` errors, and a
silently-unenforced schema invariant. The same is true today of the PLAN work,
which was nowhere near green despite existing for long enough to accumulate
610 lines. Gate results are only meaningful with a timestamp and a clean
target directory attached.

### F5 — Unpushed history *(low)*

Seven local commits, including the entire Phase 5 and Phase 6 (OBSERVE)
deliverables, have never been pushed to `origin/main`. There is no second
copy of this work off the machine. Recommendation: push before or alongside
the PLAN wiring change.

### Positive findings

For balance, the things that were checked and held up:

- **No correctness bugs in committed code.** No test failures, no clippy
  warnings, no fmt drift, on a clean rebuild.
- **The boundary test is genuine enforcement**, and it passes against the real
  tree, not a stub.
- **Live integration tests exist and pass** against both real servers — 13 of
  them. Most projects in this category have only mock-based tests.
- **Documentation is current, not aspirational.** The README was rewritten when
  Phase 5 made "no persistence" false. Phase docs record rejected approaches,
  which is more useful to a reviewer than a clean success narrative.
- **A `.gitattributes` was added** (`* text=auto eol=lf`) to stop
  `core.autocrlf=true` from rewriting every file's line endings on each commit.
- **History was reconciled deliberately**, not by force-push: the local line and
  the rebranded remote had no merge base, a file-by-file comparison showed
  `crates/` was byte-identical at the Phase 2 tips, so the local commits were
  cherry-picked onto the remote line with only `README.md` conflicting.

## 7. Suggested next actions, in order

1. **Add `pub mod plan;` to `director-app/src/lib.rs`** and fix whatever the
   compiler reports. This converts 610 lines of dead code into 610 lines of
   tested code and is the single highest-value change available.
2. **Commit the PLAN work** once it compiles, with the graph module and the
   app module as separate commits.
3. **Push.** Seven commits are unbacked-up.
4. Continue the loop in the order it runs: PLAN → ASSIGN → MONITOR → VERIFY →
   REPLAN, one step at a time, compiling after each.
5. Consider a CI gate that fails if a `.rs` file exists in `src/` that is not
   declared as a module — the boundary test already proves how valuable an
   executable architectural rule is, and F1 is exactly the class of error such
   a test catches.
